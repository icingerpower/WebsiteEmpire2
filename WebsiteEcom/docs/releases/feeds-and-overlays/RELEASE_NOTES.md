# Release Notes — Catalog Feeds + Conversion Overlays

**Date:** 2026-07-11
**Tickets:** TICKET-033 (catalog feeds), TICKET-034 (lead capture overlay),
TICKET-035 (recent-purchase social proof)
**ADRs:** ADR-026 (catalog feeds), ADR-027 (conversion overlays)

## What shipped

### Catalog feeds (new `feeds` app)
- Token-protected, pre-generated Google Shopping / Facebook Dynamic Product Ads XML feeds,
  one item per active product variant.
- Per-store `FeedConfig` (enable toggle + products-to-sync scope: all products or specific
  collections), `StoreFeedToken` (one rotatable token per store, `secrets.token_urlsafe(32)`,
  gates every feed URL), `FeedTarget` (one row per store × provider × storefront-language ×
  target country — the generation/status state machine).
- Feed URLs: `/feeds/<provider>/<country>-<lang>.xml?token=…`. Files are generated by a
  30-minute debounced beat task plus a nightly full rebuild, written atomically
  (`tempfile.mkstemp` + `os.replace()`), and served from a dedicated `FEEDS_ROOT` directory
  that is never web-served (not under `MEDIA_ROOT`).
- Every excluded product/variant is recorded with an explicit, never-silent reason
  (`no_image`, `quotation_mode`, `presale_no_date`, `no_translation`,
  `unknown_inventory_mode`) visible on the store-admin feed card.
- Prices are converted through the existing currency resolver into the feed country's
  display currency; a missing exchange rate is a loud error, never a silent fallback to the
  store's own currency.
- `g:link` always points at the canonical primary permalink URL — never an A/B variant URL
  (A/B variant URLs do not exist anywhere in this engine yet; a named regression test is
  already in place and documented as the activation trigger for when that feature, T042,
  eventually lands).
- A one-click "copy feed URL" button and per-target status banners were added to the
  store-admin feed changelist.
- `"feeds"` was added to the platform's reserved top-level slug list, closing a gap left open
  since the original URL-reservation pass.

### Lead capture overlay (new `engagement` app, part 1)
- Per-store, per-campaign lead-capture overlays (exit-intent/time-delay triggers, four themes,
  a client-side frequency cap, page exclusions) presented through the existing slot-registry
  mechanism used elsewhere in the storefront.
- Signup is a single antispam-protected POST (honeypot + rate limit, reusing the platform's
  existing primitives — nothing new invented there) that idempotently issues a shared discount
  code via the same reward-issuance pattern used by marketing campaigns, and merges into the
  existing customer record.
- Single opt-in is the platform default; stores that target Germany (detected as: they serve a
  German storefront edition, or they ship to Germany from any enabled storefront edition) fall
  back to double opt-in — marketing consent is withheld until the shopper clicks a
  confirmation link.
- A discount code linked to a lead-capture reward must itself be provenance-tagged for lead
  capture, preventing a merchant from accidentally wiring in a high-value, unrelated code.
- The overlay-theme picker in the admin is now a visual preview gallery (radio buttons behind
  the scenes — no behavior change from a plain dropdown, just a friendlier UI).

### Recent-purchase social proof (new `engagement` app, part 2)
- A small, cached, inline-embedded feed of recent purchases shown as a toast on the storefront
  — "Someone in France bought X" — with no public API endpoint of its own.
- Ships **anonymous-only** at launch: only `anonymous` display mode can be enabled by any
  store today. The schema and admin scaffolding for two additional named display modes exist
  but are inert platform-wide behind a code-level flag until a legal/privacy review clears
  them — this is enforced even against a hand-edited or legacy database row, not just at the
  admin form.
- Disabled by default per store; only PAID orders are ever considered; only a coarse
  time-of-purchase bucket and the buyer's country are ever shown; anonymized customers are
  always excluded regardless of the display mode.

## Notable fixes folded into this release
Six security findings raised during the pre-release safety audit were fixed and independently
re-verified before this release: a feed-file storage location that had made the token gate
bypassable via `/media/feeds/…` (the one release-blocking finding, now resolved by moving feed
files to a dedicated, non-web-served directory); a crash on non-ASCII feed tokens; a token
rotation that was not actually being logged; a lead-capture email-confirmation link that did
not check it was being redeemed on the correct store's domain; a honeypot response that was
subtly distinguishable from a real success response; and an inline JSON payload that did not
escape `<` before being marked safe for template embedding.

## What did not ship / was deliberately deferred
- Pinterest as a feed provider, a dedicated GTIN/barcode field, timed-promo sale-price dates,
  per-variant color/size attributes, and item-level shipping blocks are all named, approved,
  future enhancements (ADR-026's P-1/P-4/P-5/P-6/P-7/P-8) — not part of this release, not
  blocking it.
- Named (non-anonymous) social-proof display modes remain disabled platform-wide pending
  legal/privacy sign-off.
- A/B variant URLs (T042) are not part of this or any prior release; the feeds test suite
  already contains the exact assertion that will need a negative-case counterpart the day
  that feature ships.

## Dependencies
No new third-party dependencies were added for this release (`requirements.txt` unchanged by
this wave).
