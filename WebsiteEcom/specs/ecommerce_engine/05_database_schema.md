# 05_database_schema

> Initial entity outline — owned by Architect Agent. Design document, NOT Django model code.
> Derives from ADR-001…007 (`09_architecture_decisions.md`), `02_feature_matrix.md`, and the binding lessons in `design-pattern-ideas.txt` (§ references).

**Status: FIRST PASS (2026-07-02).** Field lists show the 5–10 most important fields per entity; exhaustive column specs come per-area later.

## Conventions & hard rules

- **HARD RULE (ADR-001):** every store-scoped entity carries a `store` FK — no exceptions. All such entities extend the `StoreOwnedModel` base with the `StoreScopedManager` (unscoped queries raise).
- **Scope tags:** `[S]` store-scoped (has `store` FK), `[G]` platform-global (super-admin / control plane), `[H]` hybrid (global master, store-visible or store-overridable).
- Money fields are integer minor units + currency code. Prices are tax-inclusive everywhere (DECIDED 11:#6).
- All slugs pass through the single NFD slug function (ADR-005 / §II). All internal URLs resolve via `PermalinkResolver` (ADR-005 / §III) — no entity stores a resolved href.
- Explicit status enums on every async entity (§XV-3); append-only ledgers for money movements.
- `PENDING` marks fields/entities blocked on open decisions in `11_uncertainties_to_validate.md`.

## New CRITICAL uncertainties surfaced by this pass (for human input)

1. **Authorization-amount vs capture-amount semantics per processor (ADR-007).** The capture-window model captures *more* than the authorized amount when an upsell is accepted (original + upsell in "one combined capture"). Stripe allows over-capture only in limited cases/regions; PayPal rules differ. Options: (a) auth original + separate second auth+capture for the upsell, (b) auth an inflated amount up front (customer sees a larger pending charge), (c) capture original + new charge for upsell using a saved payment method token. Each has different buyer-visible and PSD2/SCA implications. **Blocks the connector spec and the Safety Agent review scope.**
2. **DecisionLog vs order routing for the combined capture.** If the upsell capture must go through a *different* processor call than the original authorization (option c above), does the upsell charge re-enter the routing engine (possibly landing on a different Organization/merchant-of-record for the same customer order)? Needs a rule: upsell charges always follow the original order's DecisionLog outcome.
3. **Store ↔ Organization relationship for config sharing.** Part E treats Organizations purely as payment legal entities, but area 28 says "sub-stores under one organization sharing super-admin config". If a second grouping concept exists ("store groups"), it needs its own entity; if Organizations double as config-sharing parents, hybrid `[H]` entities need an `organization` scope option instead of platform-global. Currently modeled as platform-global single instance — must be confirmed before any `[G]` entity ships.
4. **Event-table volume strategy.** With impressions per product card, high-traffic stores generate millions of Event rows/day. The 90-day raw retention default may still exceed a single-Postgres budget. Need a target order of magnitude (visits/day across all stores) to choose plain table vs partitioning vs a separate analytics DB (the §VI "three databases, three sharing semantics" lesson suggests keeping analytics writes off the transactional DB).
