Rendered via consent.slot_provider.ConsentSlotProvider into {% render_slot "consent" %} (storefront/templates/storefront/base.html) — every page type, including checkout (base_checkout.html inherits the slot unmodified) and the thank-you page. Structure: - .consent-banner — fixed bottom bar, ONLY rendered when `show_banner` is True (undecided state). Three equal-weight actions: Accept all / Refuse all / Customize. - .consent-panel — ALWAYS rendered (even once a decision exists), hidden via the `hidden` attribute, so the footer "Cookie preferences" button (storefront/templates/storefront/partials/consent_manage_button.html) can reopen it without a fresh server round-trip. Both root divs carry `data-nosnippet` (F2, docs/seo/ CONSENT_BANNER_SEO_REVIEW.md) — this is server-rendered raw HTML on every page, so without it Google can select the consent copy as the SERP snippet for pages with a weak meta description. Zero behavior change; keep it on both elements if this markup is ever restructured. Vanilla JS, no build step (ADR-025 D5, T029-B), CSRF handled exactly like chat_widget.html's csrfToken() helper (reads the `csrftoken` cookie — never a {% csrf_token %} hidden input, this is a JSON fetch POST, not a form submit). data-analytics / data-marketing / data-am-objected on the root element capture the PRE-decision server-known state so the inline JS can compute "at least one category newly granted" (ADR-025 D3 reload-on-grant) without guessing at client-side state.
